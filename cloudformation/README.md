# CloudFormation templates

Version-controlled templates Pictacular's onboarding flow sends Users to launch in their own
AWS Console (issue #146 / ADR-0006), replacing the old manual access-key-pair paste. Each
template provisions an IAM Role that trusts Pictacular's own AWS account (the STS trust anchor
provisioned in issue #148, see `docs/aws-account-setup.md`), scoped to a fixed per-connection
External ID, so Pictacular can call `sts:AssumeRole` and operate on the User's bucket without
ever handling a long-lived access key.

- `create-bucket.yaml` — "create a new bucket" mode (issue #149): provisions a brand-new
  private bucket (with Pictacular's required CORS rule) alongside the Role.
- `connect-bucket.yaml` — "connect an existing bucket" mode (issue #151): scopes the Role to a
  bucket the User already owns (named as a stack parameter, not created by this stack), and
  merges Pictacular's required CORS rule into whatever CORS configuration already exists there
  via a Lambda-backed custom resource — a bucket this stack doesn't create can't otherwise be
  declared as an `AWS::S3::Bucket` resource without CloudFormation trying to manage/replace its
  properties outright.

`ExternalId`/`AllowedOrigin` are common to both templates and always pre-filled by Pictacular
via the Launch Stack URL's query string (`...&param_ExternalId=...&param_AllowedOrigin=...`).
Both templates also pre-fill `RoleName` (generated by Pictacular ahead of time, so it can
predict the resulting Role's ARN without asking the User to paste anything back — see
`server/api/storage-connections/launch.post.ts`, and confirms the stack has finished via a
direct `sts:AssumeRole` call rather than querying CloudFormation's own stack Outputs).
`create-bucket.yaml` additionally pre-fills `BucketName` (generated by Pictacular, same
rationale as `RoleName`). `connect-bucket.yaml`'s own `BucketName` parameter is *not*
pre-filled — naming the bucket to connect is the one thing Pictacular has no way to know ahead
of time, so it's the only value a User launching either template ever has to type by hand.

Linted in CI (`.github/workflows/cfn-lint.yml`) with
[`cfn-lint`](https://github.com/aws-cloudformation/cfn-lint) on every change under this
directory. Template *contents* aren't exercised by this app's Vitest suite (a Vitest black-box
test can't meaningfully assert on CloudFormation resources/policies) — `cfn-lint` plus a manual
launch in a real/sandbox AWS account is the validation path instead.
